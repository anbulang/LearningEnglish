# HN-020 家长试用与非技术验收闭环

更新时间：2026-06-13

## 目的

`HN-020` 把“上传讲义 -> AI 校对 -> 课程详情 -> 复习 -> 报告”这条主链从工程验证推进到真实家长可试用验收。

它解决的问题不是“功能是否已经存在”，而是：

1. 家长能不能不靠开发解释完成主链。
2. 产品或测试同学能不能按同一张清单记录问题。
3. 发现的问题能不能按优先级进入修复批次。
4. 试用证据能不能落到固定目录，供后续复查。

## 适用对象

- 真实家长或接近真实家长的内部试用者。
- 产品、测试、运营同学。
- 陪跑试用的开发同学。

## 范围

本期只覆盖家长端核心学习主链：

1. 进入上传讲义。
2. 拍照或从相册选择讲义图片。
3. 等待 AI 识别并进入 AI 校对。
4. 确认课程详情。
5. 完成一次复习。
6. 查看报告页是否反映本次学习。

登录、手机号绑定、孩子档案创建属于试用前置条件，只记录是否阻塞试用，不作为本期主链可用性评分重点。

## 不在本期范围

- Admin 后台运营体验。
- Android 分发策略。
- iOS TestFlight / UDID 分发决策。
- 口语评分深度体验。
- 长期多周学习效果评估。

这些问题可以作为发现项记录，但不要混入 `HN-020` 的通过判定。

## 试用前置条件

### 环境

- API 与 worker 已启动。
- App 已安装到可试用设备。
- App 指向当前可访问的 API，例如 `http://<current-host-ip>:8000/v1`。
- 当前 provider 路径已明确：`qwen + DashScope media + DashScope speech`、stub/mock，或其他指定组合。

### 试用素材

- 至少 1 份真实讲义图片。
- 最好包含 2 页以上，覆盖单词、句子、图片、题目或活动说明。
- 如果试用者愿意，优先使用孩子当天或近期实际讲义。

### 记录方式

建议把证据放到：

```text
dist/harness/HN-020/
```

可先生成记录模板：

```bash
make harness-hn020-parent-pilot-template
```

推荐文件名：

- `parent-pilot-summary.json`
- `parent-pilot-notes.md`
- `parent-pilot-upload-screen.png`
- `parent-pilot-ai-review-screen.png`
- `parent-pilot-lesson-detail-screen.png`
- `parent-pilot-review-screen.png`
- `parent-pilot-report-screen.png`

`dist/harness/` 是本地证据目录，默认不提交 git；PR 或交接时只引用摘要和关键结论。

## 通过判定

### 总体通过

一次 `HN-020` 家长试用可以判为通过，必须同时满足：

- 试用者可以完成上传、AI 校对、课程详情、复习和报告查看。
- 每一步都有明确的下一步动作，不依赖开发口头提示。
- 失败或等待状态有中文解释和可理解的恢复动作。
- 课程详情中能看到与讲义相关的核心词或句子。
- 报告页能让试用者理解本次学习已经被记录。

### 总体不通过

出现以下任一情况，判为不通过：

- 试用者无法找到上传入口。
- 上传后长时间不知道系统在做什么。
- AI 校对页内容无法让试用者判断是否该确认。
- 课程详情看不到可学内容，或图片 / 音频大量缺失且没有解释。
- 复习入口不明显，或完成后不知道下一步。
- 报告页没有任何可理解变化，且没有说明数据何时更新。

## 主链验收清单

### 1. 上传讲义

目标：家长能自然理解“我现在要把讲义拍进去”。

检查项：

- [ ] 资料库或首页能找到上传入口。
- [ ] “拍照”和“从相册选择”文案清楚。
- [ ] 选择图片后显示缩略图，而不是文件名。
- [ ] 多页讲义能显示页码和来源。
- [ ] 上传前不要求家长填写标题、老师名、主题等非必要表单。
- [ ] 上传按钮状态清楚，未选图时不会误导。
- [ ] 上传失败时能看到中文原因和重试动作。

需要记录：

- 试用者是否知道应该点哪里。
- 是否对“上传讲义”与“创建课程”关系产生困惑。
- 是否觉得拍照 / 相册流程多余或重复。

### 2. AI 校对

目标：家长能理解 AI 正在识别什么，并能决定是否确认。

检查项：

- [ ] 处理中状态不会像卡死。
- [ ] 识别结果按图片或内容块展示，能追溯到讲义原图。
- [ ] 标题、主题、核心词、句子和图片内容描述可读。
- [ ] 低置信度、缺失项或异常有中文提示。
- [ ] “确认”与“重新识别 / 重试”动作清楚。
- [ ] 失败时不展示大段英文技术错误。

需要记录：

- 家长是否知道为什么要校对。
- 哪些 AI 内容看起来不可信。
- 是否需要逐项编辑，还是只读确认足够。

### 3. 课程详情

目标：家长确认后能看到一份可以立刻使用的课程。

检查项：

- [ ] 课程标题和主题与讲义相关。
- [ ] 每个核心词或句子有清楚的文本、释义或学习说明。
- [ ] 原始讲义图片或裁剪参考可见。
- [ ] 自动生成配图加载中、成功、失败状态清楚。
- [ ] 美音 / 英音 TTS 有可理解的入口或状态。
- [ ] 媒体未完全补齐时，不阻塞查看课程。
- [ ] 课程详情能自然引导到复习。

需要记录：

- 家长是否相信这份课程来自自己的讲义。
- 是否理解“图片 / 音频异步补齐”。
- 哪些内容过多、过少或顺序不合理。

### 4. 复习

目标：孩子或家长能完成一轮最小复习。

检查项：

- [ ] 复习入口明显。
- [ ] 每道任务知道要做什么。
- [ ] 图片、文字、发音之间的关系清楚。
- [ ] 答题反馈清楚。
- [ ] 完成后有明确结束状态。
- [ ] 完成后能回到课程或报告。

需要记录：

- 试用者是否能独立完成一轮。
- 哪个任务最容易误解。
- 是否需要更短、更适合孩子的提示文案。

### 5. 报告

目标：家长能看懂这次学习留下了记录。

检查项：

- [ ] 报告页入口明显。
- [ ] 本周学习、复习或讲义数据有可理解变化。
- [ ] 报告能解释孩子练了什么。
- [ ] 报告能给出下一步建议。
- [ ] 没有数据时有清楚空态。
- [ ] 数据未更新时有可理解的刷新或延迟说明。

需要记录：

- 家长是否觉得报告可信。
- 哪个数字或图表看不懂。
- 家长最想看到但目前没有的信息。

## 问题分级

### P0：阻断试用

家长无法继续主链，或必须靠开发操作才能继续。

示例：

- 无法上传。
- AI 校对一直处理中且没有恢复动作。
- 确认后进不了课程详情。
- 复习无法开始或无法完成。
- 报告页崩溃。

### P1：严重困惑

主链能继续，但家长明显不知道系统在做什么，或对结果不信任。

示例：

- 上传后不知道是否成功。
- AI 结果看起来和讲义无关。
- 课程详情里配图 / 音频状态没有解释。
- 报告页数字变化无法理解。

### P2：体验打磨

不阻断、不严重误导，但会降低试用质量。

示例：

- 文案不够家长化。
- 按钮位置不顺手。
- 页面信息密度不均衡。
- 截图或图片裁剪不够美观。

## 修复批次

### Batch 0：试用前置与证据模板

目标：让每轮试用可以稳定开始、稳定记录。

内容：

- [ ] 固定 `dist/harness/HN-020/` 证据文件命名。
- [ ] 准备一份试用记录模板。
- [ ] 明确试用设备、API 地址、provider 配置和讲义素材。
- [ ] 试用前跑一次最小 smoke，避免把环境问题误判成产品问题。

完成标准：

- 陪跑人可以在 5 分钟内开始一次试用记录。

### Batch 1：上传与 AI 校对可理解

目标：降低第一步流失。

内容：

- [ ] 复查上传入口、拍照 / 相册按钮、图片缩略图和上传状态。
- [ ] 复查 AI 处理中、失败、重试和确认文案。
- [ ] 让 AI 校对页清楚展示“这些内容来自哪张讲义图”。
- [ ] 禁止默认展示英文底层错误给家长。

完成标准：

- 试用者能独立完成上传和校对，不需要开发解释。

### Batch 2：课程详情与复习可使用

目标：让家长确认后立刻觉得“这是一份可学课程”。

内容：

- [ ] 复查核心词 / 句子数量是否适合一次学习。
- [ ] 复查讲义原图、裁剪图、生成配图和 TTS 状态。
- [ ] 复查课程详情到复习的入口和完成后的回流。
- [ ] 标出媒体异步补齐的等待和失败状态。

完成标准：

- 家长能理解课程内容，孩子能完成一轮最小复习。

### Batch 3：报告可信度

目标：让家长知道学习结果被记录，并知道下一步做什么。

内容：

- [ ] 复查报告页是否反映本次讲义和复习。
- [ ] 复查无数据、少数据和刚完成复习后的状态。
- [ ] 增加更家长化的解释和下一步建议。
- [ ] 把不可信或延迟更新的数据明确说明。

完成标准：

- 试用者能用自己的话说出孩子今天练了什么、下一步该做什么。

### Batch 4：异常与恢复路径

目标：把真实试用中最常见的失败转成可恢复体验。

内容：

- [ ] worker 未启动、provider 超时、局域网不可达、token 失效都有中文解释。
- [ ] 关键失败态都有重试、刷新或返回动作。
- [ ] 失败态 evidence 可以被陪跑人快速定位到 API/worker 日志。

完成标准：

- 试用失败时能明确归因：环境问题、provider 问题、产品体验问题或代码缺陷。

## 与现有 Harness 的关系

- `HN-019` 证明真机主链和后端 evidence 可以跑通。
- `HN-020` 证明非开发试用者能不能理解并完成这条主链。
- `non-technical-pilot-guide.md` 是试用操作手册。
- 本文是验收清单、问题分级和修复批次入口。

如果 `HN-019` 失败，优先修工程链路；如果 `HN-019` 通过但 `HN-020` 失败，优先修可用性、文案、状态解释和页面流转。
